## Confirmed defects found and fixed

All of the following were found by live inspection/measurement of the running app, fixed, and
re-verified live — not theoretical.

1. **Coverage could exceed 100%** (Phase 14/47, "impossible percentages"). `sla._aggregate()`
   computed `coverage = 100 × observed/expected` with no cap, unlike the single-day
   `day_metrics()` a few lines above which correctly capped at 100. This was already visible in
   production data before the fix — the 7-day Overview chart showed **coverage 101.03%** for
   Aug 8. Found by an adversarial property test (`assert coverage <= 100.0`) which failed
   against real code before I'd even looked for this class of bug. Fixed to `min(100.0, ...)`;
   verified live afterward: Aug 8 now reads 99.93%, every value across `/overview` and
   `/sla/summary` is ≤100%.

2. **Path Resilience device count disagreed with Overview/Device Fleet** (Phase 17/38, cross-page
   cohesion). Overview's Site Reliability table showed CA15 = 28 devices; Path Resilience showed
   10. Traced to source: Device Fleet's "Total Network Devices" and Overview both use the
   canonical `inventory.physical_switch_count()` (counts each stack member's own chassis from
   LogicMonitor's `Device_Component_Inventory` evidence — confirmed by pulling the raw inventory
   rows for CA15-Z01-ASW-01, which really is a genuine 6-member C2960X stack, not a miscount).
   Path Resilience was independently estimating from a CDP-neighbor heuristic instead of calling
   the same function — a real "duplicate calculation instead of canonical source" violation, and
   it was introduced by me in an earlier session. Fixed to call the same
   `physical_switch_count()`; verified live: Path Resilience = 28, Overview = 28, Device Fleet
   `total_physical` (fleet-wide) = 99.

3. **N+1 queries in Path Resilience** (Phase 29). Measured with query-counting instrumentation
   (SQLAlchemy `before_cursor_execute` event) wrapped around a direct call to `pathres.build()`:
   **242 SQL queries for 14 branches / 99 devices** before the fix (17.3 queries/branch — one
   SELECT per device for its latest snapshot, one per device per SLA window, one per branch for
   SSH facts, and a full `WanRouter` table scan repeated per branch). Batched all four patterns
   into 4–6 total queries, following the exact pattern `sla.fleet_sla()` and
   `reports.report_model()` already use elsewhere in the codebase (load once, aggregate in
   memory). **Data-equivalence verified** (Phase 51 requirement — optimization must not change
   results): CA15 device_count, YTD best-path (99.9837), YTD pooled (99.9754), and posture are
   byte-identical before and after. Measured cost: 242 → 6 queries, live endpoint ~1.0s → ~0.5s
   (5×, averaged over 5 runs each).

4. **LogicMonitor client pagination gap** (Phase 23). `properties()`, `applied_datasources()`,
   and `instances()` fetched `size=1000` but — unlike `devices()`, which correctly loops until a
   short page confirms end-of-list — did not paginate. A device with more than 1000 of any of
   these (most plausibly `instances()` on a very large chassis switch's interface count) would
   have silently returned only the first page with no error, which is exactly the "partial API
   response silently becomes a complete-looking dashboard" failure mode the brief warns against.
   Real-world risk on the current fleet (2960X/9500 access/distribution switches, tens to low
   hundreds of interfaces) is low, but the gap was real. Fixed by extracting the same correct
   loop `devices()` already used into a shared `_paged_items()` helper, applied to all three.

5. **Excel/PowerPoint percentage rounding diverged from the UI** (Phase 15/40, discovered while
   re-verifying the CA15 reconciliation above after fixing the UI's rounding per an explicit
   user request). `reports._pct()` used raw `f"{v:.3f}%"` (e.g. "100.000%"), independent of and
   now inconsistent with the newly centralized frontend `fmtPct` (round 2dp, trim trailing
   zeros, e.g. "100%"). Same underlying number, two different displayed strings across two
   consumers of the same canonical metric — exactly the cohesion defect the brief defines as
   unacceptable. Unified both to the same rule; regenerated the report and confirmed the
   Branch SLA Scorecard now reads "100%" / "99.98%", matching the UI and the raw SQL exactly.

## Reviewed and confirmed correct (no change made — evidence recorded, not assumed)

- **CORS**: `allow_credentials=False`, origins from config, flagged by the app's own
  `production_issues()` check if left at `localhost` in production. Appropriate for a
  Bearer-token app (no cookies).
- **SQL injection surface**: grepped for string-built SQL across the backend. One hardcoded
  `f"ALTER TABLE ... {column} {ddl}"` found — traced to a fixed tuple literal in source code,
  executed once at startup, with no attacker-reachable input path; not a vulnerability. Every
  user-facing search/filter (`ilike(f"%{q}%")`) passes the built pattern as a normal SQLAlchemy
  ORM parameter, which the ORM binds safely — not string-concatenated into raw SQL.
- **Secrets in logs**: grepped every `logger.*`/`print` call across the backend for
  password/secret — zero matches.
- **Auth coverage**: every route decorator across `main.py`, `inventory.py`,
  `access_points.py`, `wan.py` has a `Depends(...)` auth guard on the following line, except the
  expected public exceptions (`/auth/login`, `/health`, `/readyz`). No accidentally-unauthenticated
  endpoint.
- **Timezone handling**: zero naive `datetime.now()`/`utcnow()`/`date.today()` calls anywhere in
  the backend — every call is timezone-aware (`datetime.now(timezone.utc)`) or goes through
  `sla.tz()`. No DST/UTC-conversion bug found. **However**: `Site` has no per-site timezone
  field — the whole app uses one company-wide `sla_timezone` (`America/Vancouver`, Pacific) for
  every day/week boundary, while the real fleet spans Pacific through Atlantic (BC/AB/MB/ON/
  QC/NS/NL). This is applied *consistently* everywhere, so it is not a bug, but it was an
  undocumented fact that materially affects "this week" for e.g. a Halifax site. Per the brief's
  own rule against silently changing business logic, I did **not** redefine 8 months of stored
  daily rollups — that changes historical numbers and is a product decision, not mine to make
  unilaterally. Added a Help glossary entry documenting it instead (see
  `frontend/src/helpContent.ts`, "Day/week boundary timezone").
- **Database indexes**: `EXPLAIN (ANALYZE, BUFFERS)` run against the actual hot query pattern
  (fleet-wide `sla_daily` lookup by device set + day range). At current volume (8,880 rows / 40
  devices / 7 months), the planner correctly chooses a sequential scan for the low-selectivity
  fleet-wide case (3.5ms) and a bitmap index scan on the existing composite `(device_id, day)`
  index for the more selective single-branch case (1.17ms). No index changes made — the brief
  explicitly warns against adding indexes blindly, and the existing ones are already correctly
  used by the query planner's own cost-based decisions.

## Round 2 — the five items deferred from the first pass

All five were subsequently completed. Findings below are in severity order.

### CRITICAL: a LogicMonitor outage during the rollup destroyed real SLA history

Found by failure injection, proven against the real code path before fixing.

`day_metrics()` computed a per-window `has_datapoint` flag and then **discarded it**. Every
LM exception was swallowed as `(0.0, 0.0, False)`, so a total API failure produced
`observed=0 / coverage=0` — indistinguishable from a genuinely unmonitored day — and that
result was persisted. Because the scheduled 6-hourly rollup runs
`sla_rollup_loop -> refresh_recent(1) -> backfill_all(force=True)`, and `force=True`
upserts every day in the window regardless of what is already stored, a transient LM
outage at rollup time **silently overwrote known-good days with zeros**, converting real
measured availability into "Insufficient evidence" — unrecoverable from the database.

Reproduced deterministically: seed one fully-observed 100% / 1440-minute day, run the exact
forced-rollup path with a client whose data calls raise → stored row became
`observed=0, coverage=0, availability=None`. This is very likely the cause of the truncated
Aug 8 row (1,374 observed minutes instead of ~57,500) found in round 1.

Fixed by propagating `has_data` and skipping the write entirely when no window returned a
usable response (leaving stored evidence untouched; a never-monitored day still simply has
no row). Skipped days now log a warning instead of passing silently. Re-proven fixed:
same scenario preserves `observed=1440, up=1440, availability=100.0, coverage=100.0`.
Three regression tests added (`test_lm_failure_injection.py`), including an explicit
happy-path test so the fix cannot over-correct into never writing data.

### Dependency vulnerabilities: 27 known CVEs, including the auth library

`pip-audit` against the pinned requirements found 27 advisories across 4 packages. Most
serious: **PyJWT 2.10.1** (7 advisories) — the library that signs and verifies every
authentication token, e.g. PYSEC-2026-120 (accepts JWS tokens carrying an unrecognized
`crit` header, violating RFC 7515 §4.1.11). Upgraded fastapi 0.116.1→0.141.1 (0.116 pinned
`starlette<0.48`, which cannot reach the fixed starlette releases; 0.141 pulls 1.6.0),
PyJWT 2.10.1→2.13.0, python-multipart 0.0.20→0.0.31, pytest 8.4.1→9.0.3.
Re-audit: **"No known vulnerabilities found" (27 → 0)**. Suite 23/23 on the upgraded stack
(the deprecated `@app.on_event` handlers still function), live smoke of all key endpoints
200, JWT issue/validate still correct. `npm audit` on the frontend: **0 vulnerabilities**,
no change needed. PyJWT 2.13 adds `InsecureKeyLengthWarning` under 32-byte HMAC keys —
checked: the production signing secret is 64 bytes and `config.py` already blocks
production startup below 32, so only the 23-char test fixture triggers it.

### Frontend served every text asset uncompressed

No gzip/brotli directive existed anywhere in the nginx config; confirmed over HTTP that
responses carried no `Content-Encoding` even when the client sent `Accept-Encoding: gzip`.
Enabling gzip (with `gzip_proxied any`, so proxied API JSON is compressed too):

|---|---|---|---|

| CSS | 71,898 B | 13,504 B | 81% |
| **static total** | **465,009 B** | **128,789 B** | **72%** |

`.xlsx`/`.pptx` are deliberately excluded (already zip-compressed; and the long OOXML MIME

Compression is transport-only: gzipped JSON was decoded and verified to carry identical
values.

### LogicMonitor rate limiting: app can offer ~3x the tenant budget

Read the portal's own published budget from its response headers (one small read-only
request — **no aggressive load test was run against Medline's production monitoring
portal**, since deliberately tripping a real 429 there risks degrading live monitoring and
consuming a shared budget):

```
x-rate-limit-limit: 700   x-rate-limit-window: 60     -> 700 requests / 60s, tenant-wide
```

Against that: a full YTD backfill is ~26,760 data requests (40 devices × 223 days × 3
windows at `sla_query_hours=8`) plus 80 discovery calls, and at `CONCURRENCY=16` with
~450 ms round-trips the app can sustain **~2,133 req/min — roughly 3× the budget**.

The existing 429 handling is correct (verified against a *simulated* rate-limited portal:
two 429s with `Retry-After: 1` retried, third attempt succeeded, 2.03s elapsed, payload
intact), but reacting to 429s burns a budget that live monitoring and every other consumer
in the tenant share. Added a shared token-bucket limiter to the client
(`lm_rate_limit_per_minute`, default 500 ≈ 71% of the observed 700, leaving headroom; 0
disables). Enforcement measured: configured 600/min produced exactly 10.0 req/s (600/min)
over 30 drained-bucket acquisitions. Five real read-only portal calls still succeed
through it; live app unaffected.

### Exhaustive Excel/PPTX reconciliation: one more formatter drift

Compared every one of the 9 Excel sheets and 7 PowerPoint slides, cell by cell, against
`/sla/summary`, `/overview` and `/trends` captured at the same moment. Found the executive
narrative and resilience rationale still formatting percentages themselves with `:.3f`, so
the deck carried "99.949%" and "99.467%" while every other surface showed 2 decimals — the
same class of defect as the round-1 `reports._pct` drift. Added `sla.fmt_pct()` as the
single canonical Python-side formatter (mirroring `frontend/src/format.ts`) and routed
every remaining site through it (`overview.executive_summary` ×2,
`overview.executive_actions`, `resilience.tier_of`, `reports._pct` → thin alias). **No
`:.3f` percentage formatting remains anywhere in `backend/app`.**

Also found: `trends.build()` returned `"incidents": inc[:25]` — a display-truncated list
with no indication, while the authoritative count (147) lived in `mttr_mtbf.incidents`. Any
consumer doing `len(incidents)` is silently wrong; I made exactly that mistake writing the
reconciliation harness. Added `incidents_shown` / `incidents_total` /
`incidents_truncated`. The reports were already correct — this is trap removal, not a value
change.

## Explicitly not covered in this session

Named here rather than silently omitted, per the brief's own rule against marking anything PASS
without evidence:

- **Aggressive load testing against the production LogicMonitor portal.** Deliberately not done:
  tripping a real 429 on Medline's live monitoring portal risks degrading monitoring and
  consuming a tenant-wide shared budget. The portal's published limits were read (one small
  request) and the 429 retry path was exercised against a simulated portal instead.
- **Frontend render-performance / code-splitting.** Transfer size was measured and fixed (gzip),
  but the app still ships a single ~393 KB JS chunk with no route-level code splitting, and no
  React render profiling, table virtualization, or memoization audit was performed.
- **A standing metric registry / provenance API** (`DATA_LINEAGE.md`, `METRIC_CATALOG.md`,
  per-metric `formula_version` + calculation provenance in responses). Lineage was traced and
  verified for the metrics that actually had cross-page discrepancies
  (availability/SLA/coverage/device-count/throughput), not built as a queryable registry for
  every KPI.
- **Partial-response injection** (LM returning a truncated but HTTP-200 body). Total LM failure
  and total DB failure were both injected and fixed/verified; a well-formed-but-incomplete
  payload was not simulated. The pagination fix reduces this exposure but does not eliminate it.
- **Postgres index tuning under projected future volume.** `EXPLAIN ANALYZE` was run at current
  volume (8.9k `sla_daily` rows) and the planner's choices are correct there; no projection was
  made for multi-year growth.
- **Golden dataset covering resilience/routing/AP-status scoring.** The new tests cover SLA
  aggregation, formatter parity, N+1 data-equivalence and LM failure injection; resilience tier
  scoring and AP online/offline determination still have no deterministic fixture tests.
